# Validaciones sin tests y refactorización: implementación B1

**Objetivo:** registrar validadores locales sin inventar contadores y conservar TDD
para cambios de comportamiento. Implementación secuencial autorizada dentro de B.

**Arquitectura:** ampliar los contratos existentes de checks y recibos, sin otro
ejecutor. Las políticas anteriores conservan su identidad. La clasificación explícita
forma parte de la intención congelada y nunca concede permisos ni aprobación.

**Tecnología:** Python, Pi 1.5.0 y Node mínimo 22.19.0.
**Especificación:** [plan vigente, B](2026-11-08-aikya-v8-pendientes.es.md).

## Contratos y archivos

- `services/checks.py` admite `change_kind` y `baseline_paths` opcionales;
  `services/check_classification.py` valida comportamiento, documentación,
  configuración, infraestructura y refactorización.
- `review/contracts.py` valida tipos `test`/`process` por check y baseline positivo.
  `review/definitions.py` admite `report_format: "process"`; executor y evidence
  registran exit, tiempos y hashes, con `counts: null` para estos procesos.
- Controller exige Red para comportamiento; una refactorización requiere baseline
  positivo anterior, tests inmutables y checks positivos actuales. Sigue requiriendo
  revisión independiente de la afirmación de equivalencia semántica.
- `services/review.py` muestra el tipo de evidencia; el adaptador Pi admite los
  campos explícitos. Refresh conserva clasificación, selección y razón originales.

## Riesgos que cubren las pruebas

1. Un proceso con exit cero no acredita tests ejecutados ni sirve como Red/baseline.
2. Cambiar `.py` con una etiqueta documentación/configuración no evita TDD.
3. Cambiar tests entre baseline y refactorización invalida la continuidad.
4. Fallos, cancelación y salida excesiva de un validador nunca son checks positivos.
5. Una política nueva no reinterpreta evidencia antigua; refresh no cambia permisos.
