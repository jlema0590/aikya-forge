# Parches y operaciones multifichero: implementación B3

**Objetivo:** editar archivos grandes con anclas exactas y aplicar lotes pequeños
revisados, sin ampliar el mensaje del modelo ni repetir efectos inciertos.
**Arquitectura:** ampliar `aikya_write` manteniendo su sustitución simple; el lote
requiere un change_id nativo vigente del autor. Reutilizar grants efímeros, scopes
ODD/SDD, calidad, recibos, memoria y documentación canónicos. No añadir shell.
**Tecnología:** Python y Pi/TypeScript; Node mínimo 22.19.0.
**Especificación:** [pendientes B](2026-11-08-aikya-v8-pendientes.es.md).

## Contratos

- Intento de lote: `{change_id,operations:[{path,content}|{path,edits:[{old,new}]}|{path,delete:true}]}`.
  Máximo 20 destinos únicos, dentro del scope congelado y una selección vigente.
  Intento máximo 12.000 bytes JSON canónico; archivos de texto hasta 1 MB.
- Cada ancla old debe existir exactamente una vez en el original y no solaparse
  con otra. Mostrar old/new exactos, hashes completos y acción; no truncar cambios.
  Una eliminación exige mostrar el contenido completo, limitado al paquete revisable.
- `services/batch_inputs.py` valida/compone sin efectos; `source_batches.py`
  previsualiza y aplica con grant `file.batch` ligado a candidato/archivos/workflow.
  Mantener el protocolo de 16 KB y los límites comunes de líneas/pie Markdown.
- Extraer verificación de grants a `authorization_tokens.py`, manteniendo el formato
  anterior de `file.write`. El modelo no recibe claves, aprobación ni recuperación.
- Reservar antes de efectos y comprobar todos los destinos antes del primer cambio
  y otra vez antes de cada archivo. Escrituras nuevas exclusivas, readback exacto,
  informe en el dossier del change_id y memoria local; ningún check se inventa.
- El lote no es una transacción atómica de varios archivos ni aislamiento del SO.
  Ante cambios concurrentes/fallo conservar archivos y estado pendiente; no revertir
  automáticamente cambios de usuario. Los procesos externos no comparten el lock.
- `batch_recovery.py` reconoce solo efectos completos exactos de una reserva
  firmada y termina bookkeeping tras confirmación; parcial/desconocido queda manual.
  Acceso nativo mediante `/aikya-verify {"action":"recover-batch"}`; el modelo no
  puede aprobar ni reutilizar grants caducados.
