# Continuidad y recuperación documental: implementación B2

**Objetivo:** permitir actualizaciones documentales confirmadas dentro de una
iteración TDD/RDD y reconciliar operaciones conocidas sin volver a escribirlas.
**Arquitectura:** usar el registro firmado de operaciones documentales existente;
conservar hashes anteriores/posteriores y base Git como testigo del host. No crear
otro almacén de memoria ni excluir globalmente los documentos de los candidatos.
**Tecnología:** servicios Python y comandos nativos Pi existentes.
**Especificación:** [pendientes B](2026-11-08-aikya-v8-pendientes.es.md).

## Contratos

- `review/document_transitions.py`: validar únicamente transiciones completas,
  firmadas, de la misma sesión y base Git sobre páginas canónicas no ejecutables.
  Metodología, features, specs, tools e instrucciones quedan fuera. Un cambio manual,
  otra sesión, hash modificado o transición pendiente no amplía el alcance.
- `review/candidates.py`: `require_scope(previous,candidate,root=None)` mantiene
  el rechazo estricto sin root; con root acepta solo esos deltas documentales.
  Checks/revisión previos no se transfieren al nuevo candidato.
- `services/review.py`: incluir las páginas documentales observadas en el paquete
  final, respetando el límite compartido de 6.000 bytes. Escalar si no caben.
- `services/documentation.py` reserva antes de escribir el manifiesto y los hashes
  revisados; su operación final firmada guarda el testigo compacto.
- `services/documentation_recovery.py`: `preview(root,session_id)` muestra hashes y
  estado; `apply(root,plan,approved=False)` solo finaliza bookkeeping tras comprobar
  todos los efectos exactos y la ausencia de cambios ajenos. No reejecuta escrituras.
- `/aikya-docs {"action":"recover"}` requiere confirmación del resultado concreto;
  sin UI devuelve confirmation_required. Efectos parciales/desconocidos permanecen
  pendientes para reconciliación manual.
